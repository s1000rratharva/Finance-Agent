# FinSight AI

**A production-oriented AI financial research & analysis platform** — not another PDF
chatbot.

FinSight answers analyst-grade questions over preloaded company fundamentals (Reliance
Industries, TCS, Infosys) **and** your own uploaded filings, using hybrid RAG with
page-level citations, SQL + Python for every number, agentic task routing, interactive
charts and workspace-level data isolation.

## Architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Next.js 16 (App Router, TS, Tailwind 4)                                 │
│  landing · auth · dashboard · companies · compare · chat · documents ·   │
│  evaluations        TanStack Query · Recharts · cookie session           │
└────────────────────────────────┬─────────────────────────────────────────┘
                                 │  REST + httpOnly JWT cookie
┌────────────────────────────────▼─────────────────────────────────────────┐
│  FastAPI (async) — /api/v1/*                                             │
│                                                                          │
│  api/          health · auth · workspaces · companies · documents ·      │
│                chat · analytics · evaluations                            │
│  services/                                                                 │
│    agents/     router LLM → tool plan (rag|sql|python|chart|compare|risk)│
│    rag/        rewrite → dense+BM25 → RRF → rerank → citations          │
│    ingestion/  PDF·DOCX·XLSX·CSV loaders → text + numeric extraction     │
│    financials/ SQL query builders · Python calculator · risk scoring     │
│    llm/        Groq client + central prompt registry                     │
│    storage/    S3-compatible object store (R2 / MinIO)                   │
│    evaluation/ RAGAS harness (graceful retrieval-only fallback)          │
│  db/           SQLAlchemy 2 async models: users, workspaces, documents,  │
│                chunks, conversations, companies, financial_statements    │
└───────┬───────────────────────────────┬─────────────────┬────────────────┘
        │                               │                 │
┌───────▼──────┐              ┌─────────▼────────┐  ┌─────▼──────────────┐
│ PostgreSQL   │              │ ChromaDB         │  │ Object storage     │
│ source of    │              │ per-workspace    │  │ R2 (prod) / MinIO  │
│ truth + BM25 │              │ vector collections│ │ (dev) / local disk │
│ rebuild base │              │                  │  │                    │
└──────────────┘              └──────────────────┘  └────────────────────┘
```

**Key design decisions**

| Concern | Decision | Why |
| --- | --- | --- |
| Numbers | Never generated by the LLM | Statements live in Postgres; derived metrics come from a guarded Python calculator |
| Retrieval | BM25 + vector, fused with **Reciprocal Rank Fusion** | Rank-based fusion needs no score normalisation across wildly different scales |
| Isolation | Chroma collection **per workspace** + `workspace_id` on every query | Tenancy enforced at the storage layer, not just in application filters |
| Reranking | Cross-encoder → LLM pointwise → pass-through | Quality degrades gracefully with zero extra dependencies |
| Storage keys | `/{workspace_id}/{document_id}/{filename}` | A leaked key alone never crosses a tenant boundary |
| SQL access | Whitelisted tables + `SELECT`-only static checks | The LLM never gets unbounded SQL execution |
| Python access | AST allow-list (no imports/attributes/lambdas) | Expressions run in an empty-`__builtins__` namespace |

## Quickstart

### Prerequisites

- Node.js 20+
- Python 3.11–3.12 (3.13+ works, minus RAGAS — see note below)
- Docker (for Postgres + Chroma) — or run your own

### 1. Environment

```powershell
Copy-Item .env.example .env
Copy-Item backend\.env.example backend\.env
Copy-Item frontend\.env.example frontend\.env.local
```

The three files are read by different processes:

| File | Read by | What to set |
| --- | --- | --- |
| `.env` | `docker compose` | Postgres/MinIO passwords, `JWT_SECRET`, `GROQ_API_KEY`, CORS, public API URL |
| `backend/.env` | `uvicorn` / the backend container when run outside compose | `DATABASE_URL`, Chroma host/port, `GROQ_API_KEY`, auth/S3 settings |
| `frontend/.env.local` | Next.js | `NEXT_PUBLIC_API_URL` |

Put a **new** Groq key (get one at <https://console.groq.com/keys>) in
`backend/.env` when following steps 3–4, or in root `.env` when using
`docker compose up --build`. Everything else has working local defaults.
Never commit these files.

### 2. Start infrastructure

```powershell
docker compose up -d postgres chroma
```

### 3. Backend

```powershell
cd backend
python -m pip install -r requirements.txt        # add -eval for RAGAS on ≤3.12
python -m scripts.seed                           # load Reliance / TCS / Infosys
python -m uvicorn app.main:app --reload --port 8000
```

### 4. Frontend

```powershell
cd frontend
npm install
npm run dev
```

Open <http://localhost:3000>, create an account, and you land in an isolated
workspace with the sample companies preloaded.

### Docker (all-in-one)

```powershell
docker compose up --build
```

### Make shortcuts

```powershell
make help       # list targets
make install    # backend + frontend deps
make seed       # load sample data
make test       # backend test suite
make up / down  # docker compose
```

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | Liveness + dependency checks (postgres, chroma, groq) |
| POST | `/auth/register` | Create account + default workspace, sets cookie |
| POST | `/auth/login` | Authenticate, sets httpOnly cookie |
| GET | `/auth/me` | Current user |
| POST | `/auth/logout` | Clear cookie |
| GET/POST | `/workspaces` | List / create workspaces |
| GET | `/workspaces/current/stats` | Document, chunk, conversation counts |
| GET | `/companies` | Company catalogue |
| GET | `/companies/{slug}` | Company + full statement history |
| GET | `/companies/{slug}/ratios` | Derived ratios (computed in Python) |
| GET | `/companies/compare/{metric}` | Cross-company series (`?slugs=a,b`) |
| GET/POST | `/documents` | List / upload (PDF·XLSX·CSV·DOCX) |
| GET | `/documents/{id}/chunks` | Inspect extracted chunks |
| POST | `/documents/{id}/reprocess` | Re-run extraction + indexing |
| DELETE | `/documents/{id}` | Delete file, chunks and vectors |
| POST | `/chat` | **Run the agentic RAG pipeline** |
| GET | `/chat/conversations` | Thread history |
| GET | `/analytics/{slug}/overview` | KPI block with YoY deltas |
| GET | `/analytics/{slug}/trends` | Multi-year series (`?metrics=a,b`) |
| GET | `/analytics/{slug}/ratios` | Ratio history |
| GET | `/analytics/{slug}/risks` | Risk flags + summary |
| GET | `/analytics/{slug}/insights` | AI narrative over the KPI block |
| POST | `/evaluations/run` | Start a RAGAS run |
| GET | `/evaluations/runs` | Evaluation history |

Auth is a httpOnly cookie; every data request also carries `X-Workspace-Id`, which the
backend authorises against membership before touching any row.

## How an answer is produced

```
user question
   │
   ├─ 1. rewrite      follow-up → self-contained query (Groq, JSON mode)
   │                   └─ failure ⇒ use original query, marked "skipped"
   │
   ├─ 2. route        LLM classifies: rag | sql | python | chart | compare | risk | general
   │                   └─ emits an ordered tool plan
   │
   ├─ 3. retrieve     dense (Chroma, workspace collection)
   │               +  sparse (BM25 over Postgres chunks)
   │                   └─ Reciprocal Rank Fusion (k=60, weights 1.0 / 0.85)
   │
   ├─ 4. rerank       cross-encoder → LLM pointwise → pass-through
   │
   ├─ 5. act          tool plan executes: SQL (whitelisted), Python (AST-guarded),
   │                   chart spec generation, risk scoring, insights
   │
   └─ 6. generate     Groq answers ONLY from the numbered passages,
                      citing [n] markers, with the numbers already verified
```

Every step appends a `TraceStep` (name, status, duration) that the chat UI renders as
an expandable **agent trace**, so you can always see *why* an answer looks the way it
does.

## Testing

```powershell
cd backend
python -m pytest -q
```

**45 tests, zero external services required** — they cover:

- API smoke + auth guards (no DB connection needed)
- Password hashing, JWT round-trip, expiry and tamper rejection
- Financial maths: CAGR, margins, liquidity, leverage, returns, cash flow
- Risk scoring: high-leverage vs. healthy statements
- Chunking, overlap behaviour, Indian-format number parsing (`1,02,592.50`, `(1,234)`, `₹45.6 cr`)
- RRF fusion ordering, weighting and `top_k`; positive BM25 scores on fresh workspaces
- Loaders and extraction across PDF/CSV/Excel/text, table → numeric fact mapping

For a live end-to-end check (auth → upload → retrieval → chat → evaluation →
tenant isolation), start the API and run the 58-assertion smoke script:

```powershell
cd backend
python scripts/smoke_api.py http://127.0.0.1:8000
```

It creates unique test users on every run, so it is safe against a persistent
database. Without `GROQ_API_KEY`/Chroma it still verifies graceful degradation
and BM25-grounded citations.

Frontend:

```powershell
cd frontend
npm run typecheck   # tsc --noEmit
npm run lint
npm run build
```

## Deployment roadmap

| Stage | Target | Notes |
| --- | --- | --- |
| 1 | **Vercel** | Frontend only; point `NEXT_PUBLIC_API_URL` at the API, or use the `/backend` rewrite |
| 2 | **Render** | FastAPI web service + Docker runtime; managed Postgres add-on |
| 3 | **Neon** | Serverless Postgres — create branches per environment, set `DATABASE_URL` |
| 4 | **Cloudflare R2** | Set `S3_ENDPOINT_URL`, `S3_BUCKET`, R2 access/secret keys; no egress fees |
| 5 | **Chroma** | Self-host `chromadb/chroma:1.5.9` with a persistent `/data` volume, or use Chroma Cloud (needs a `CloudClient` adapter) |
| 6 | **Docker** | `backend/Dockerfile` + `frontend/Dockerfile` are ready; add a production compose override |

### ChromaDB in production

Chroma is a **derived index**, not the source of truth. Postgres keeps the text
chunks; each workspace gets a collection named `ws_<workspace_id>`. A fresh
Chroma instance therefore needs `python -m scripts.seed` and reprocessing of
uploaded documents (`POST /api/v1/documents/{id}/reprocess`) before RAG returns
citations. `CHROMA_COLLECTION` in the env file is informational only.

**Option A — self-hosted Chroma server (works with the current code)**

Run the official image as its own service with a persistent volume/disk mounted
at `/data`. Chroma moved its container data path from `/chroma/chroma` to `/data`
in v1.0, and this repo pins 1.5.9.

```yaml
chroma:
  image: chromadb/chroma:1.5.9
  environment:
    CHROMA_PERSIST_PATH: /data
    ANONYMIZED_TELEMETRY: "FALSE"
  volumes:
    - chromadata:/data
  ports:
    - "8001:8000"   # host port; the container listens on 8000
```

Backend settings for that service:

```env
CHROMA_HOST=chroma     # service DNS name inside the network, not localhost
CHROMA_PORT=8000       # internal container port
```

On Render, create a Docker web service from `chromadb/chroma:1.5.9`, attach a
persistent disk at `/data`, keep it at **one instance** (Render disks are bound
to a single service instance), and set `CHROMA_HOST` to the internal hostname,
for example `finsight-chroma:8000`.

**Option B — Chroma Cloud (managed/serverless)**

Create a database at <https://trychroma.com> and use the values from its Connect
panel:

```env
CHROMA_HOST=api.trychroma.com   # or the region-specific endpoint
CHROMA_PORT=443
CHROMA_API_KEY=...
CHROMA_TENANT=...
CHROMA_DATABASE=...
```

`backend/app/services/rag/vector_store.py` currently constructs an
`HttpClient`; Cloud needs `CloudClient` with API-key auth. Ask for that adapter
before choosing Option B. Option A needs no code changes.

Do **not** use in-memory/embedded Chroma in production, and never point a
serverless backend at `localhost`.

Pre-deployment checklist

- [ ] Rotate `JWT_SECRET` to ≥ 32 random bytes (`openssl rand -hex 32`)
- [ ] Set `ENVIRONMENT=production` (JSON logging) and `GROQ_API_KEY`
- [ ] Set `COOKIE_SECURE=true`. Keep `COOKIE_SAMESITE=lax` behind the same-origin `/backend` rewrite; use `none` only for a cross-site API + frontend. `ENVIRONMENT=production` alone does not change cookie flags.
- [ ] Set `CORS_ORIGINS` to the exact frontend origin(s) when calling the API directly
- [ ] Give Chroma a persistent `/data` volume and reindex/seed it after first deploy
- [ ] Replace sample company data with audited figures
- [ ] Run Alembic migrations instead of `create_all`
- [ ] Move document processing to a real worker (Celery/Arq) for large uploads
- [ ] Add rate limiting on `/auth/*` and `/chat`
- [ ] Run the RAGAS suite and record a baseline before launch
